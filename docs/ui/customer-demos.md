# Customer demos

Operate-mode extension of the existing Birdeye console. Preserve its dark/light themes, system typography, native controls and History rail. This surface implements five distinct product UIs using the existing bounded recipes, Runner CU accounting and saved runs. The user rejected generic text-only demo reports; product-specific layouts and interactions are the surface requirement.

The Demos workspace uses five navigation buttons, a collapsed Details disclosure and a compact query form. Before a snapshot exists, one short prompt replaces the empty product layout. Selecting a demo does not run a paid snapshot. Create draft prepares a free plan, checks inputs and the CU limit, then fetches Birdeye evidence in the same submission. Product controls operate on the loaded snapshot without additional API calls.

| Product | Implemented interaction and visual evidence | Data boundary |
| --- | --- | --- |
| Research terminal (`terminal`) | Watchlist with symbol/address filter, descending volume/liquidity/24h-change sorting, selectable token rows, market/control inspector and liquidity comparison bars. | One discovery page with bounded enrichment. Liquidity bars share the largest observed value in the full watchlist as their scale, including when filtered. They do not represent price history. |
| DEX token inspector (`dex-inspector`) | Market metrics, pool table sorted by liquidity, relative liquidity bars and a selected-pool inspector with controls and source disclosure. | Only the fetched pool page. Reported liquidity is not executable depth, route selection or a swap quote. |
| Wallet intelligence (`wallet-intelligence`) | Starts with Discover smart wallets, a filterable wallet shortlist, token-level evidence disclosures and free wallet selection. A separately previewed and executed analysis shows 7-day/30-day buttons, realized/unrealized PnL bars centered at zero, holdings allocation and position details. | Discovery returns traders of smart-money-list tokens in provider order; it establishes neither verified smart-money status nor profitability. Token PnL is never summed into wallet-wide PnL. Analysis periods overlap and remain separate. Allocation covers priced holdings on the fetched page; missing prices are not zero balances. |
| Security signals (`security-signals`) | Three rule panels with threshold markers and All/Attention/Unknown filter, followed by 38 supporting metrics/observations in market, ownership, controls and authority sections, plus a wallet-holder table. One closed Details disclosure per metric group exposes source, timestamp, basis and exact values. | Liquidity triggers below its threshold; top-10 token-account concentration triggers above its threshold; freezeability triggers when observed. Unknown remains unknown. Within threshold and not observed are not safety verdicts. Empty threshold panels request a snapshot instead of showing an invented threshold. |
| Telegram research brief (`telegram-brief`) | Local chat preview with a research command, structured bot reply, controls and coverage; Inspect plain text toggle and Export message action. | Preview only, with no Send action or delivery claim. Live lookups query Birdeye; message generation and saved snapshots are local. Delivery, scheduling and bot credentials belong to the customer's integration. |

Inputs invalidate the prepared plan. A plan belongs to its exact input; a late response cannot start a run after selecting another History entry or leaving the workspace. Reopening through History resets the form and prepared plan to the selected saved run. Create draft requires any required address and a sufficient integer CU budget. The button and form controls are disabled while preparing or running; an active run exposes progress and Stop. CU estimates exclude retries and are not confirmed billing. Drafts use live evidence and persist as ordinary saved runs.

Wallet intelligence opens discovery without an address input. It uses the fast Smart Wallets recipe: one 1-day smart-money token page of up to 20 tokens, followed by one 30-day top-trader page of up to 10 rows for each selected token. The Maximum tokens / wallets control accepts 1–5 (default 3), bounding both token lookups and the valid, deduplicated wallet shortlist. Provider order is preserved. Discovery costs at most 110 estimated CU at the default limit (20 + 3 × 30), or 80 at limit 2, before retries; it does not fetch wallet PnL or holdings. The source-page disclosure retains the full fetched token page, and each candidate exposes its observed tokens, token-level volume/PnL, window, source and observation time. Empty or budget-blocked discovery does not invent candidates.

Selecting a wallet only prepares its read-only address, clears any prepared plan and focuses Create draft. That button checks the plan and requests only the selected wallet’s analysis, separately estimated at 90 CU for 7d/30d PnL and holdings. Discovery and analysis are separate saved runs titled with `discover` or the shortened wallet address. Reopening a saved discovery shortlist in History allows another selection without API calls. CLI `--address` remains available for direct analysis. Reports distinguish `walletStage: discovery` and `walletStage: analysis`; older analysis reports remain recognizable through their saved input address. The two-stage control wraps, selected addresses wrap, and discovery tables use the existing local scrolling behavior; rendered responsive fit remains unverified.

Results and original inputs persist in SQLite and reopen from History without paid API calls. The result identifies its timestamp and subject separately from editable inputs, with saved/reused state, CU, API attempts, uncertainty, coverage and missing evidence. Editing the query does not alter the displayed snapshot. All reports export evidence JSON; Telegram also exports plain text. Saved input, full sources, calculation notes and the integration command remain inspectable.

Source evidence disclosures show request IDs and observation times. Address controls reuse click-to-copy behavior. Timestamp formatting accepts Unix seconds, Unix milliseconds and ISO strings; invalid values show Time unavailable. Decimal-aware formatting and sorting distinguish small prices, zero, negative amounts and missing data. Compact display rounds amounts intentionally; source values remain inspectable. Bars are visual ratios, not additional observations. Older snapshots lacking new fields continue to render unknown values without fetching replacements. Telegram reports now include an Observed token controls section; legacy reports without it remain unknown.

The surface uses existing semantic colors, focus treatment, disclosures and flat panel borders, with inline icons, relative bars and chat bubbles specific to these views. There are no new global tokens or raster assets. The History rail follows the existing 950px layout breakpoint. Product inspectors and wallet columns stack at 1200px; at 650px navigation wraps, market metrics use two columns, wallet metrics stack, and security panels and Telegram columns become single-column. Security evidence uses two columns above 900px and stacks below; concentration shares use independent bars, and the five-column holder table scrolls locally. Tables retain local scrolling and source text wraps. These are source-defined behaviors, pending rendered verification.
