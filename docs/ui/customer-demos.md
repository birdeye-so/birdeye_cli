# Customer demos

Operate-mode extension of the existing Birdeye console. Preserve its dark/light themes, system typography, native controls and History rail. This surface implements five distinct product UIs using the existing bounded recipes, Runner CU accounting and saved runs. The user rejected generic text-only demo reports; product-specific layouts and interactions are the surface requirement.

The Demos workspace uses compact icon navigation with five labels: Market, Token & pools, Wallets, Security and Telegram. The selected product title sits above one query toolbar. CU limit stays beside Create draft; Security thresholds open in a separate disclosure. About, CLI command and API steps remain inspectable without a separate preview gate. Before results, a short subject-specific empty state points to the required action. Selecting a product uses no data requests. Create draft prepares the plan, validates inputs/budget and fetches evidence in one submission.

Mode: **Operate**. Inherit the existing navy/light console, system type, blue action accent and semantic status colors. The result is the main reading surface. Keep the query, run metadata, result and supporting evidence visually separate; avoid repeating the product title in the result header.

A compact snapshot bar shows status, timestamp, subject, estimated CU and Export JSON. Partial evidence has a visible notice; complete-for-requested-scope reports are not mislabeled as partial. Missing evidence, full source JSON and API attempts are below the product view. Running, stopped and error states retain their actions. Old snapshots preserve explicit unavailable values.

Input changes invalidate the plan. Late plan responses cannot start work after a History change or leaving Demos. Drafts are live evidence runs saved in History. Estimates exclude retries and are not confirmed billing. The form respects the current optional CU limit; a blank limit follows the application's unlimited setting.

Wallet intelligence opens discovery without an address input. It uses the fast Smart Wallets recipe: one 1-day smart-money token page of up to 20 tokens, followed by one 30-day top-trader page of up to 10 rows for each selected token. The Maximum tokens / wallets control accepts 1–5 (default 3), bounding both token lookups and the valid, deduplicated wallet shortlist. Provider order is preserved. Discovery costs at most 110 estimated CU at the default limit (20 + 3 × 30), or 80 at limit 2, before retries; it does not fetch wallet PnL or holdings. The source-page disclosure retains the full fetched token page, and each candidate exposes its observed tokens, token-level volume/PnL, window, source and observation time. Empty or budget-blocked discovery does not invent candidates.

Selecting a wallet only prepares its read-only address, clears any prepared plan and focuses Create draft. That button checks the plan and requests only the selected wallet’s analysis, separately estimated at 90 CU for 7d/30d PnL and holdings. Discovery and analysis are separate saved runs titled with `discover` or the shortened wallet address. Reopening a saved discovery shortlist in History allows another selection without API calls. CLI `--address` remains available for direct analysis. Reports distinguish `walletStage: discovery` and `walletStage: analysis`; older analysis reports remain recognizable through their saved input address. The two-stage control wraps, selected addresses wrap, and discovery tables use the existing local scrolling behavior; rendered responsive fit remains unverified.

Results and original inputs persist in SQLite and reopen from History without paid API calls. The result identifies its timestamp and subject separately from editable inputs, with saved/reused state, CU, API attempts, uncertainty, coverage and missing evidence. Editing the query does not alter the displayed snapshot. All reports export evidence JSON; Telegram also exports plain text. Saved input, full sources, calculation notes and the integration command remain inspectable.

Source evidence disclosures show request IDs and observation times. Address controls reuse click-to-copy behavior. Timestamp formatting accepts Unix seconds, Unix milliseconds and ISO strings; invalid values show Time unavailable. Decimal-aware formatting and sorting distinguish small prices, zero, negative amounts and missing data. Compact display rounds amounts intentionally; source values remain inspectable. Bars are visual ratios, not additional observations. Older snapshots lacking new fields continue to render unknown values without fetching replacements. Telegram reports now include an Observed token controls section; legacy reports without it remain unknown.

Layout uses named CSS containers, so the actual workspace width determines the split even when History is expanded. At 900px of result width, token inspectors, wallet analysis and Telegram export stack. At 600px, market/pool/discovery rows become labeled two-column records, metric lists use one column, rule conditions span the row, and form actions become full width. Dense holder and position tables keep local horizontal scrolling. Product navigation and metric categories scroll within their own rows. Numeric text can wrap for unusually small prices or large amounts; exact values remain in titles and evidence.
